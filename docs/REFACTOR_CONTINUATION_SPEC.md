## 1. 현재 판단

**Django 기능을 Bun + TypeScript로 옮긴 초안은 상당 부분 존재하지만, 기능·화면·운영 검증이 완료되지 않은 상태입니다.** 프레임워크를 다시 선정하거나 처음부터 구현하기보다, 현재 구현의 오류를 고치고 기존 동작과 대조한 뒤 구조를 정리하는 방식이 적합합니다.

현재 변경은 커밋되지 않았습니다. 추적 파일 69개에 변경이 있고 그중 44개는 삭제 상태이며, `src/`, `tests/`, `scripts/`, `package.json`, `bun.lock` 등 신규 구현은 Git 미추적 상태입니다. 삭제된 Django 구현은 기준 커밋에서 조회할 수 있습니다. 코드 감소량을 기능 이전 완료율로 해석해서는 안 됩니다.

과거 기록상 기본 방향은 **기존 DB 호환·이관 제외, 기존 UI와 HTML 디자인 최대한 유지**였습니다. 현재 README와 구현도 이 방향을 따릅니다. 이번 제안은 이를 전제로 하며, 실제 데이터 이관이나 디자인 개편이 필요하다면 별도 범위로 확정해야 합니다.

## 2. 시스템 구조와 업무 흐름

관리자가 팀원·회차·문항·매칭을 준비하면, 시작 시 Slack PIN 작업이 생성됩니다. 리뷰어는 PIN으로 해당 회차에 로그인해 임시 저장 및 제출을 수행합니다. 관리자가 마감 또는 전원 제출 조건의 생성 액션을 실행하면 HTML과 PDF를 만들고, 검토 후 Slack으로 전달합니다.

| 계층 | 현재 구현 | 판단 |
|---|---|---|
| HTTP 서버 | Bun + Hono, `src/index.ts`, `src/app.ts` | 구현됨. 관리자 기능과 인증이 한 파일에 집중됨 |
| 화면 | Nunjucks + 기존 `core/templates`, `core/static` | 기존 CSS·JS·폰트는 현재 추적 diff 없음. 템플릿은 변환됨 |
| 데이터 | `bun:sqlite`, SQLite WAL, 직접 SQL | 신규 DB 사용. 스키마 버전 기록은 있으나 순차 변경 실행기 없음 |
| 업무 규칙 | `src/domain.ts` | 회차·PIN·매칭·검증·원자적 제출·CSV 구현 |

### F-02. 부분 발송 후 재생성 시 발송 상태 불일치 — P0

- 재현: 두 보고서 중 하나 성공·하나 실패 → 성공한 보고서를 동일 내용으로 재생성 → 재승인.
- 관찰: 성공 보고서가 `SENT/is_sent=1`에서 `APPROVED/is_sent=0`으로 바뀝니다. 작업은 기존 `DONE`, `FAILED` 두 개만 남고 새 발송 작업은 생기지 않습니다.
- 원인: 재생성은 발송 상태를 초기화하지만, 발송 중복 방지 키는 보고서 ID와 HTML 해시에 묶여 있고 기존 완료 작업은 그대로 남습니다.
- 계획: 생성물 버전·승인 대상·발송 이력을 연결합니다. 동일 생성물 재생성은 기존 발송 이력을 보존하고, 변경된 생성물은 별도 승인 대상으로 취급하는 방식을 권장합니다.
- 완료 기준: 동일 내용 재생성, 내용 변경, 일부 성공, 명시적 실패, 결과 불명확, 재시작 각각에서 상태가 일관되고 의도하지 않은 중복 발송이 없어야 합니다.

### F-04. 컨테이너 바인딩 설정 충돌 — P1

- 근거: `.env.example`의 `HOST=127.0.0.1`, `Dockerfile`의 `HOST=0.0.0.0`, `docker-compose.yml`의 `.env` 주입, `src/index.ts`의 `HOST` 사용.

- 계획: 컨테이너 내부 `HOST=0.0.0.0`을 Compose에서 명시하고 호스트 공개 범위는 포트 매핑으로 제한합니다.
- 완료 기준: 예제 설정으로 만든 컨테이너에 호스트에서 `/health/` 접근 성공. 이번에는 Docker 빌드·기동을 수행하지 않았습니다.

### F-05. 문서·검증·운영 상태의 불일치 — P1

- 개발 서버 가이드는 삭제된 `manage.py`, Django migration 및 테스트 명령을 안내합니다.

- 커스텀 양식 가이드는 297 × 167mm 및 서버 이미지 경로를 설명하지만, 현재 변환기는 1280 × 720px 페이지를 강제하고 data URL을 사용합니다.

- 계획: 안내를 현재 동작으로 통일하고 ‘자동 사전 점검’과 ‘관리자 시각 검수 완료’를 구분합니다. 배포·복구 절차와 실행 가능한 검증 명령을 함께 문서화합니다.

## 5. 구현 방향 제안

### 5.1 현재 기술 조합 유지, 책임과 타입 정리

Bun + Hono + Nunjucks + SQLite를 유지하는 것을 권장합니다. 기존 화면을 보존하려는 목적에 맞고, 지금 확인된 문제는 프레임워크 교체 없이 해결할 수 있습니다.

`src/app.ts`의 인증/세션, 리뷰어, 회차, 팀원, 문항/매칭, 보고서, 메시지 기능을 점진적으로 분리합니다. HTTP 계층은 입력·권한·응답을 담당하고, 업무 규칙과 트랜잭션은 서비스 계층에 둡니다. 파일 이동 전에 실패를 고정하는 회귀 검증을 마련합니다.

`Row = Record<string, any>`가 DB 행, 화면 데이터, 작업 payload에 광범위하게 쓰입니다. 회차·보고서·세션·작업별 타입과 페이지별 ViewModel을 정의해 이번 이력 화면처럼 필수 데이터가 빠지는 문제를 조기에 잡는 것을 권장합니다. SQL을 전부 ORM으로 교체하는 작업은 포함하지 않습니다.

### 5.2 새 SQLite DB에도 스키마 변경 절차 도입

현재 `CREATE TABLE IF NOT EXISTS`와 버전 1 삽입만으로는 기존 Bun DB의 컬럼 변경을 처리할 수 없습니다. 순서가 있는 스키마 변경, 적용 기록, 실패 시 트랜잭션 롤백을 도입합니다. 기존 Django DB 이관과는 별개입니다.

빈 DB 초기화와 이전 Bun 스키마 업그레이드를 모두 검증합니다. 운영은 현재처럼 단일 인스턴스를 전제로 하며, 다중 워커·Redis·PostgreSQL 도입은 별도 요구가 생겼을 때 판단합니다.

### 5.3 보고서와 발송 상태를 운영자가 이해할 수 있게 정리

- HTML 생성, PDF 변환, 관리자 승인, Slack 발송 상태를 각각 표시합니다.
- 승인에 생성물 버전 또는 해시를 연결하고, 내용 변경 시 승인이 유효한지 명확히 처리합니다.
- `FAILED`는 정책에 따라 재시도하고, `UNKNOWN`은 수신 여부 확인 후 관리자가 결과를 확정할 수 있게 합니다.
- 재시작 복구로 `UNKNOWN`이 된 작업은 `delivery_logs`가 없을 수 있습니다. 현재 메시지 화면은 해당 로그를 기준으로 조회하므로, 작업 기준으로 모든 확인 필요 항목을 표시하는지 검증·보완합니다.
- 일부 보고서 생성 실패가 있어도 일괄 작업 자체는 `DONE`으로 끝날 수 있습니다. 회차 화면에서 개별 실패와 재처리 대상을 명시합니다.
- 긴 답변은 원문을 임의로 자르지 않고 후속 슬라이드에 이어 싣는 방향을 권장합니다. 페이지 수 변화는 디자인 승인 대상입니다.

### 5.4 기능 보존표를 먼저 확정

기존 라우트가 존재하는 것만으로 이전 완료로 보지 않습니다. Django의 58개 테스트 시나리오를 ‘유지 / 의도적 변경 / 폐기 / 미검증’으로 분류하고 신규 검증에 연결합니다.

특히 날짜 검증·회차 시작 조건·부서별 자동 매칭·활성 회차 PIN 발급·CSV 인코딩·원본 이름 보존·문항 이미지·결과지 익명성·결정적 답변 정렬·사용자 양식·검수·발송 복구를 포함합니다. 삭제된 관리 명령의 운영상 필요 여부도 확인합니다.

`validation_logs`는 테이블과 조회는 있지만 현재 신규 코드에 기록 생성 경로가 보이지 않습니다. 버전도 `v1` 기본값과 로그 저장은 있지만 버전 증가 정책은 확인되지 않습니다. 단순히 화면을 유지할지, 실제 기능을 복원할지 기능 보존표에서 결정합니다.
