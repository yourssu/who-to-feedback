# 01. 재설계 배경 및 기능 범위 정의

본 문서는 기존 레거시 피어리뷰 시스템(`legacy-ts`)을 전면 폐기하고, DB 스키마 및 REST API 명세부터 재설계하게 된 배경과 기능 범위(유지 / 제거 / 보류) 의사결정 내역을 기록합니다.

---

## 1. 레거시 코드베이스 폐기 배경

초기 버전은 명확한 REST API 명세와 정규화된 DB 스키마를 먼저 정의하지 않은 상태에서 기능 추가와 런타임 마이그레이션(Django → Node/Bun → Cloudflare Workers)을 거듭하며 구현되었습니다. 그 결과 다음과 같은 구조적 복잡성이 누적되어 유지보수보다 전면 재설계가 훨씬 효율적이라고 판단했습니다.

### 1.1 프론트엔드와 백엔드의 강결합 (SSR + Form POST 혼재)
* 서버가 Nunjucks HTML 템플릿(`core/templates/*.html`)을 직접 렌더링(SSR)하고, 화면 조작의 대부분을 브라우저 기본 `<form method="post">` 전송과 `302 Redirect` + 플래시 쿠키(`peerflow_flash`)에 의존했습니다.
* 동시에 일부 기능(답변 자동 저장, 리포트 미리보기 등)은 비동기 JSON API를 호출하여, 하나의 라우터 안에 HTML 응답과 JSON 응답이 뒤섞여 있었습니다.
* 관리자 화면이 단일 뷰모델 빌더(`buildAdminStatusPageModel`)에 과도하게 결합되어 특정 탭 하나를 열어도 회차·문항·매칭·리포트·발송이력·검증로그 전체를 조회해야 했습니다.

### 1.2 이중 런타임 추상화로 인한 복잡도 폭발
* 로컬 Node/Bun 실행 환경(로컬 디스크 파일시스템 + `node:sqlite` + 로컬 Playwright)과 Cloudflare Workers 서버리스 환경(D1 + R2 + Queues + Durable Objects + Browser Rendering)을 동시에 지원하기 위해 무거운 어댑터 계층(`PlatformAdapter`, `src/platform.ts`, `src/workers/platform.ts`)을 두었습니다.
* 비즈니스 로직 곳곳에 런타임 분기 코드가 침투하여 코드 추적과 디버깅이 어려웠습니다.

### 1.3 비정규화된 DB 스키마와 임시방편적 상태 추적
* **비정형 JSON 쿼리 의존**: `jobs` 테이블의 `payload` 텍스트 컬럼 내부를 SQLite `json_extract(payload, '$.cycleId')`로 매번 파싱하여 작업 상태를 조회했습니다.
* **리포트 데이터 혼재**: `reports` 테이블의 `html` 텍스트 컬럼에 실제 HTML 문자열을 넣기도 하고 `"r2:reports/..."` 문자열 프리픽스를 넣어 R2 경로로 해석하기도 하는 등 저장 방식이 일관되지 않았습니다.
* **DB 트리거 기반 변경 감지**: 답변·문항·매칭 테이블에 `AFTER INSERT/UPDATE/DELETE` SQL 트리거를 걸어 `report_input_epoch` 카운터를 증가시키고 리포트의 `input_epoch`와 비교하는 복잡한 방식으로 재생성 필요 여부를 판단했습니다.
* **동적 키 기반 임시 저장**: `assignments.draft_data`에 `{"q_12": "4", "q_15_3": "checked"}`처럼 프론트엔드 HTML `<input name>` 속성에 종속된 문자열을 그대로 직렬화해 저장했습니다.

### 1.4 과도한 부가 기능 및 테스트 분기 침투
* 실제 운영 환경에서 거의 쓰이지 않는 부가 기능(커스텀 HTML 템플릿 업로드 및 플레이스홀더 검증, 동명이인/오타 레벤슈타인 유사도 병합 제안, 글자 수 기반 슬라이드 넘침 추정, `UNKNOWN` 발송 상태 수동 결재 등)이 핵심 파이프라인을 복잡하게 만들고 있었습니다.
* 운영 코드 내부에 `TEST_MODE`(가상 시간 이동, 데모 시드 자동 생성, 원클릭 로그인 등) 분기가 깊숙이 섞여 있었습니다.

## 2. 재설계 핵심 원칙

1. **Cloudflare 서버리스 단일 타깃**: 로컬 파일시스템이나 Docker/Playwright 이중 지원을 완전히 제거하고, **Cloudflare Workers + Pages(Static Assets) + D1 + R2 + Queues + Browser Rendering** 환경만 단일 타깃으로 삼습니다.
2. **프론트엔드·백엔드 완전 분리**: 백엔드는 **OpenAPI 3.1.0 표준을 엄격히 준수하는 순수 JSON REST API**만 제공하고, 프론트엔드는 정적 SPA(`web/`)로 분리합니다.
3. **정규화된 D1 스키마 및 R2 분리**: D1에는 정규화된 관계형 데이터와 사람이 읽을 수 있는 R2 객체 키(`image_r2_key`, `html_r2_key`, `pdf_r2_key`)만 저장하며, 파일 본문은 모두 R2에 저장합니다.

## 3. 기능 범위 의사결정 (유지 / 제거 / 보류)

재설계 과정에서 확정한 기능별 유지·제거·보류 결정 내역입니다.

### 3.1 유지(In-Scope) 기능
| 영역 | 유지 기능 상세 |
| :--- | :--- |
| **인증 및 보안** | • 최초 실행 시 초기 관리자 계정 생성 (`/api/auth/setup`)<br/>• 관리자 아이디/비밀번호 로그인 및 리뷰어 회차별 6자리 숫자 PIN 로그인<br/>• `HttpOnly` 세션 쿠키 + `X-CSRF-Token` 이중 검증 및 로그인 5회 실패 시 15분 잠금 |
| **팀원 관리** | • 팀원 단건 등록·조회·삭제 (`name`, `email`, `department`, `slack_user_id`)<br/>• CSV 파일 일괄 업로드 (이메일 기준 Upsert, 오류 행 발견 시 즉시 `422` 응답 및 전체 롤백) |
| **회차 및 설문 문항** | • 회차(`DRAFT` → `ACTIVE` → `COMPLETED` → `CLOSED`) 생명주기 관리<br/>• 4종 문항 유형(`RATING`, `TEXT`, `SINGLE_CHOICE`, `MULTIPLE_CHOICE`) 및 선택지 관리<br/>• **문항별 참고 이미지 첨부 (최대 10MB, PNG/JPEG/WebP, R2 저장)** |
| **매칭 및 리뷰 수집** | • 수동 개별 매칭 및 자동 매칭 (`ALL` 전체 교차 / `SAME_DEPARTMENT` 동일 부서 교차)<br/>• 리뷰어 대시보드, 구조화된 JSON 답변 임시 저장(Draft), 원자적 최종 제출(Submit) |
| **리포트 이중 생성** | • 익명화된 피드백 집계(작성자 신원 완전 분리, 서술형 가나다순 정렬) 및 SVG 차트(방사형·도넛·막대) 생성<br/>• **1280×720 슬라이드 규격의 독립형 HTML 및 PDF 리포트 이중 생성 (R2 저장)**<br/>• 생성 실패(`FAILED`) 시 **15초 주기 자동 재시도** |
| **Slack DM 발송** | • 3대 핵심 알림 자동 발송: ① 회차 시작 시 **PIN 발급**, ② 미제출자 **리마인더**, ③ 승인된 **HTML + PDF 리포트 동시 첨부 발송**<br/>• 발송 이력(`PENDING`, `SENT`, `FAILED`) 조회 및 실패 건 일괄 재시도 |

### 3.2 제거(Removed) 기능 및 사유
| 제거된 레거시 기능 | 제거 사유 |
| :--- | :--- |
| **커스텀 HTML 리포트 양식 업로드** | 필수 플레이스홀더 검증 및 깨진 레이아웃 디버깅 비용이 과도하며, 잘 다듬어진 단일 기본 슬라이드 템플릿으로 통일하는 것이 품질 유지에 유리함 |
| **이름 정규화(유사 이름 병합) 제안** | 팀원 식별의 유일 키는 `email`이므로, 레벤슈타인 거리 기반 한글 자모 유사도 계산 로직은 불필요함 |
| **불량 응답 정규식 필터링 및 수동 답변 제외** | 단순 정규식(`ㅋㅋㅋ`, 반복 문자 등)은 오탐이 잦고, 별도 `validation_logs` 테이블 및 응답 제외 토글(`is_excluded_from_report`)이 쿼리 복잡도를 크게 높임 |
| **샘플 3명만 리포트 생성(`sample`) 모드** | 비동기 Queue 환경에서는 전체 피평가자 리포트를 한 번에 생성해도 응답 지연이 없으므로 불필요함 |
| **글자 수 기반 레이아웃 점검(`layout_check`)** | 렌더러가 이미 줄 수/문항 수 기준으로 슬라이드 자동 페이지네이션(`paginateSlides`)을 수행하므로 중복 기능임 |
| **리포트별 관리자 메모(`admin_memo`) 및 체크리스트** | 실제 리포트 결과물에 반영되지 않는 단순 메모 컬럼으로, `NEEDS_REVIEW` → `APPROVED` → `SENT` 상태로 충분함 |
| **회차 버전(`v1`, `v2`) 및 `version_logs` 테이블** | `DRAFT` 단계의 문항 수정마다 버전을 올리고 로그를 쌓는 기능은 실질적 효용이 낮음 |
| **범용 자유 Slack DM 발송 메뉴(`CUSTOM_MSG`)** | 피어리뷰 시스템 본연의 역할(PIN 발급, 리마인더, 리포트 전달)을 벗어나며 스팸/오발송 위험이 있음 |
| **`UNKNOWN` 발송 상태 및 관리자 수동 확인 절차** | Slack Web API의 명확한 응답 코드로 `SENT` / `FAILED` 판별이 가능하며, 실패 시 재시도 큐로 처리하는 것이 훨씬 직관적임 |

### 3.3 보류(Deferred) 기능
* **런타임 내장 `TEST_MODE` 및 데모 시드**: 프로덕션 코드와 테스트 전용 분기가 섞이는 것을 방지하기 위해 현재 코드베이스에서는 완전히 배제했으며, 필요 시 외부 시드 스크립트나 별도 테스트 환경으로만 구성합니다 (`MOCK_SLACK_MODE` 환경 변수만 경량 시뮬레이션용으로 유지).
